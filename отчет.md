## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Улагашев Айман |
| Вариант (запрос) | Q10 «Returned Item Reporting» (вариант 2) |
| Масштаб `sfN` | sf1 |
| Почему выбрал такой масштаб | sf1 — это 6 млн строк `lineitem` и 1.5 млн `orders`, bronze занимает ~190 МБ в ZSTD (~490 МБ без сжатия). Для бенчмарка нужно было 27 раз пересоздавать bronze (9 конфигураций × 3 раунда) — на sf1 это ~15 минут, на sf10 было бы несколько часов и до 5 ГБ временных данных при свободных ~30 ГБ на диске. Docker ограничен 8 ГБ памяти, Trino получил 4 ГБ heap — sf1 с запасом помещается, и запросы не уходят в spill. Объём при этом достаточный, чтобы разница в размерах кодеков была явной. Ещё плюс: для sf1 есть эталонный ответ Q10, с которым можно сверить результат. |

## 2. Поднятые сервисы — и почему именно они

Вывод `docker ps` (`results/docker_ps.txt`):

```
NAMES             IMAGE                               STATUS                    PORTS
trino             trinodb/trino:476                   Up 33 minutes (healthy)   0.0.0.0:8080->8080/tcp
lakekeeper        quay.io/lakekeeper/catalog:v0.9.5   Up 34 minutes (healthy)   0.0.0.0:8181->8181/tcp
lakehouse-pg      postgres:17-alpine                  Up 34 minutes (healthy)   5432/tcp
lakehouse-minio   minio/minio:latest                  Up 34 minutes (healthy)   0.0.0.0:9000-9001->9000-9001/tcp
```

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Полностью совместим с API S3, поэтому Trino, Spark и Lakekeeper работают с ним штатными S3-клиентами — тот же код без изменений заработает на AWS S3 / Yandex Object Storage. Поднимается одним контейнером, есть веб-консоль для просмотра файлов. HDFS для одного ноутбука избыточен, а локальная файловая система не даёт S3-семантики. |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Lakekeeper поддерживает именно Postgres как бэкенд. Транзакционность важна: коммит в Iceberg — это атомарная замена указателя на metadata.json, и каталог должен делать это без гонок. Образ alpine лёгкий. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Реализует открытую спецификацию Iceberg REST, поэтому к одному каталогу подключаются разные движки (в работе — Trino и Spark). Написан на Rust: один бинарник, стартует за секунды и почти не ест память, в отличие от Hive Metastore (JVM + отдельная схема БД) или Nessie. Сам раздаёт настройки хранилища (warehouse), движкам не нужно знать структуру бакета. |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Есть встроенный коннектор `tpch`, который генерирует данные «на лету» — не нужно ничего скачивать. Коннектор Iceberg поддерживает CTAS, партиционирование, UPDATE/DELETE, time travel, метатаблицы `$files`/`$snapshots`. MPP-движок для интерактивного SQL: ELT и аналитика пишутся на чистом SQL. Spark для этого тяжелее (долгий старт сессии), DuckDB не умеет писать в Iceberg REST. |
| Spark 3.5.3 + Iceberg 1.7.1 | второй движок, читает bronze через тот же каталог (часть 6.2) | см. раздел 6.2 |

### Скрипты, которыми поднимал стек

Весь стек описан в `docker-compose.yml`, запуск одной командой:

```bash
cp .env.example .env
docker compose up -d          # minio, postgres, lakekeeper, trino + init-контейнеры
docker ps                     # проверка, что всё healthy
```

Что внутри compose (сокращённо):

```yaml
minio:                 # объектное хранилище, S3 API на 9000, консоль на 9001
  image: minio/minio:latest
  command: server /data --console-address ":9001"
minio-init:            # одноразовый: создаёт бакет warehouse
  entrypoint: mc alias set local http://minio:9000 ... && mc mb --ignore-existing local/warehouse
postgres:              # хранилище метаданных каталога
  image: postgres:17-alpine
lakekeeper-migrate:    # одноразовый: миграции схемы каталога в Postgres
  image: quay.io/lakekeeper/catalog:v0.9.5
  command: ["migrate"]
lakekeeper:            # Iceberg REST Catalog на 8181
  command: ["serve"]
lakekeeper-init:       # одноразовый: bootstrap + создание warehouse "lakehouse" (lakekeeper/warehouse.json)
  image: curlimages/curl
trino:                 # SQL-движок на 8080, каталоги в trino/catalog/
  image: trinodb/trino:476
```

Каталог Iceberg в Trino (`trino/catalog/lakehouse.properties`):

```properties
connector.name=iceberg
iceberg.catalog.type=rest
iceberg.rest-catalog.uri=http://lakekeeper:8181/catalog
iceberg.rest-catalog.warehouse=lakehouse
iceberg.file-format=PARQUET
iceberg.compression-codec=ZSTD
fs.native-s3.enabled=true
s3.endpoint=http://minio:9000
s3.path-style-access=true
```

Плюс `trino/catalog/tpch.properties` (`connector.name=tpch`) — генератор исходных данных.

![benchmark](results/benchmark.png)

Наблюдения:
- По размеру кодеки делятся на две группы: ZSTD/GZIP (~185–195 МБ) и SNAPPY/LZ4 (~260–290 МБ). Без сжатия ORC на 13% больше Parquet.
- Время Q10 на sf1 почти не зависит от кодека: разброс между раундами (~0.2–0.3 с) сравним с разницей между конфигурациями. Запрос ограничен джойнами и CPU, а данные после первого чтения лежат в кэше ОС локального MinIO. На полном скане разница видна: Parquet быстрее ORC, ZSTD быстрее GZIP.
- Несжатый Parquet сканируется быстрее всех только потому, что чтение с локального диска бесплатное. В реальном облаке, где за каждый байт из S3 платят временем и деньгами, в 2.5 раза меньший объём ZSTD важнее.
- Абсолютное время Q10 по основному bronze (0.52 с) меньше, чем в бенчмарке (~1.1 с): в бенчмарке запрос шёл сразу после пересоздания таблиц, и кэши метаданных и файлов ещё были холодными. Внутри бенчмарка условия у всех конфигураций одинаковые, поэтому их можно сравнивать между собой.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная OLTP-БД (Postgres) хранит данные построчно на одном сервере: хорошо для транзакций, плохо для аналитики по миллиардам строк — масштабируется только вертикально, и хранение с вычислениями нельзя разделить. Классическое DWH (Greenplum, Vertica, Snowflake) решает аналитику, но данные заперты в его закрытом формате, а хранение дорогое. Data lake (файлы в S3) дешёвый и масштабируется бесконечно, но это просто папки с файлами: нет транзакций, схемы, UPDATE/DELETE, одновременная запись ломает таблицу. Lakehouse объединяет: дешёвое объектное хранилище + открытый табличный формат (Iceberg), который даёт ACID-коммиты, схему и её эволюцию, снапшоты и time travel, партиционирование со статистикой. Хранение и вычисления разделены: одни и те же файлы читают Trino, Spark и другие движки, и вычисления можно масштабировать отдельно от данных. В этой работе это видно на практике: таблицы записаны Trino, а Spark их прочитал без копирования и получил тот же результат. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | На `silver.customer` (`scripts/evolution_time_travel.py`, лог — `results/evolution_time_travel.md`). 1) `ALTER TABLE ... ADD COLUMN customer_tier varchar` — выполнилось мгновенно, число data-файлов осталось 1: изменились только метаданные (новая версия схемы в metadata.json), старые parquet-файлы не переписывались, новая колонка в них читается как NULL. Снапшот при этом не создаётся. 2) `UPDATE ... SET customer_tier = CASE ...` (GOLD/SILVER/BRONZE/DEBT по acctbal) — это уже изменение данных: появился новый снапшот с операцией `overwrite`. 3) `RENAME COLUMN phone TO phone_number` — данные сразу читаются под новым именем, хотя внутри старого parquet-файла колонка по-прежнему называется phone. Iceberg связывает колонки по числовому field-id, а не по имени, поэтому переименование безопасно и не требует перезаписи. В Hive-таблицах колонки сопоставляются по имени или позиции, и такое переименование сломало бы чтение старых файлов. Потом имя вернул обратно, чтобы не ломать gold. |
| Пример скрипта восстановления данных из снапшота (time travel) | Сценарий «случайно удалили данные»: |

```sql
-- 1. запоминаем текущий снапшот (перед "аварией")
SELECT snapshot_id FROM lakehouse.silver."customer$snapshots"
ORDER BY committed_at DESC LIMIT 1;                        -- 4142395721619811310

-- 2. авария: удалили всех клиентов из RUSSIA
DELETE FROM lakehouse.silver.customer WHERE nation_name = 'RUSSIA';   -- 6078 строк
SELECT count(*) FROM lakehouse.silver.customer;            -- 143922

-- 3. история таблицы
SELECT snapshot_id, committed_at, operation
FROM lakehouse.silver."customer$snapshots" ORDER BY committed_at;
-- 7609793447781206439  append     (создание таблицы)
-- 4142395721619811310  overwrite  (UPDATE customer_tier)
-- 5626287416498440026  delete     (авария)

-- 4. смотрим таблицу в прошлом (time travel), ничего не меняя
SELECT count(*), count_if(nation_name = 'RUSSIA')
FROM lakehouse.silver.customer FOR VERSION AS OF 4142395721619811310;   -- 150000, 6078
-- или по времени:
-- ... FOR TIMESTAMP AS OF TIMESTAMP '2026-10-13 15:36:46 Europe/Moscow'

-- 5. восстановление: откат текущего состояния на снапшот до удаления
ALTER TABLE lakehouse.silver.customer EXECUTE rollback_to_snapshot(4142395721619811310);
SELECT count(*), count_if(nation_name = 'RUSSIA') FROM lakehouse.silver.customer;  -- 150000, 6078

-- альтернатива (точечно вернуть только потерянные строки, не откатывая остальное):
-- INSERT INTO lakehouse.silver.customer
-- SELECT * FROM lakehouse.silver.customer FOR VERSION AS OF 4142395721619811310
-- WHERE nation_name = 'RUSSIA';
```

Откат работает, потому что DELETE не удаляет старые файлы физически, а только создаёт новый снапшот без них. Поэтому после демонстрации в `silver.customer` 3 файла вместо 1 (16.7 МБ). Старые снапшоты живут, пока не выполнен `ALTER TABLE ... EXECUTE expire_snapshots(retention_threshold => '7d')` — это компромисс между возможностью отката и местом на диске.

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Apache Spark 3.5.3 + Iceberg 1.7.1 (движок) | Главное, что хотелось показать, — открытость lakehouse: таблицы записаны одним движком (Trino), а читаются другим через тот же REST-каталог, без копирования и экспорта. Spark подходит для этого лучше всего: Iceberg изначально создавался под Spark, и его Spark-интеграция — эталонная реализация спецификации с полной поддержкой записи, MERGE и процедур обслуживания (`rewrite_data_files`, `expire_snapshots`, `remove_orphan_files`), которых в Trino меньше. Для моей задачи разделение ролей такое: Trino — интерактивный SQL и BI, Spark — тяжёлые батчевые ELT и обслуживание таблиц. Doris/StarRocks — быстрые MPP-СУБД для интерактивной аналитики с дашбордов, но с Iceberg они работают в основном как с внешним каталогом на чтение, а в Trino у нас такой SQL-слой уже есть — второй такой движок дублировал бы его. Официальный образ `apache/spark` плюс два jar из Maven (iceberg-spark-runtime и iceberg-aws-bundle) — ничего собирать не нужно. |

**Скрипт развёртывания** — сервис `spark` в `docker-compose.yml` (профиль `spark`, чтобы не стартовал вместе со стеком):

```yaml
spark:
  image: apache/spark:3.5.3
  profiles: ["spark"]
  volumes:
    - ./spark:/opt/demo:ro
    - spark-ivy:/root/.ivy2            # кэш скачанных jar
  command:
    - /opt/spark/bin/spark-submit
    - --master local[4]
    - --packages org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.7.1,org.apache.iceberg:iceberg-aws-bundle:1.7.1
    - --conf spark.sql.catalog.lakehouse=org.apache.iceberg.spark.SparkCatalog
    - --conf spark.sql.catalog.lakehouse.type=rest
    - --conf spark.sql.catalog.lakehouse.uri=http://lakekeeper:8181/catalog   # тот же Lakekeeper
    - --conf spark.sql.catalog.lakehouse.warehouse=lakehouse
    - --conf spark.sql.catalog.lakehouse.io-impl=org.apache.iceberg.aws.s3.S3FileIO
    - --conf spark.sql.catalog.lakehouse.s3.endpoint=http://minio:9000         # тот же MinIO
    - --conf spark.sql.catalog.lakehouse.s3.path-style-access=true
    - /opt/demo/bronze_demo.py
```

Запуск:

```bash
docker compose --profile spark run --rm spark
```

## 7. Выводы

Медальон даёт выигрыш не столько в скорости запроса на маленьких данных, сколько в предсказуемости: bronze хранит сырую копию, и любой следующий слой можно пересобрать; в silver один раз делаются очистка, типизация и тяжёлый джойн, поэтому Q10 по silver читает в 6.7 раза меньше строк, чем по bronze (за счёт партиции по году и денормализации), а gold отвечает за 30 мс. По хранению: сжатие уменьшает данные в 2.5 раза, и среди кодеков ZSTD — лучший компромисс: почти как GZIP по размеру, но быстрее на записи (в 1.65 раза) и чтении. Формат Parquet выбран, потому что Trino сканирует его быстрее ORC и его читают все движки — это подтвердил Spark, который без копирования прочитал таблицы, записанные Trino. На sf1 время Q10 от кодека почти не зависит: запрос ограничен джойнами и CPU, а не чтением. Поэтому кодек стоит выбирать по размеру и скорости записи, а производительность запросов улучшать раскладкой данных: партициями, сортировкой и готовыми витринами.
